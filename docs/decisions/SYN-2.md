# SYN-2 · S-1 · Связь сцены с ресурсом и определения сущностей

- **Дата:** 2026-11-07
- **Область записи:** `schema/**`, `docs/contracts/**`, этот файл
- **Уточнение:** 2026-11-07, решение приёмки по имени кода N-3 (вариант B) — см. раздел
  «Уточнение по решению приёмки» ниже

Статус: accepted

## Что решено и зачем

Манифест получает законный способ связать смысловой ID сцены с ресурсом `.tscn`, а GameSpec —
способ описать сущность, не протаскивая в определение изменяемое состояние. До этой карточки связь
существовала только в коде ядра (таблица `game/runtime/scene_registry.gd`), то есть сцену нельзя было
добавить без правки ядра — это нарушало INV-11.

Изменения аддитивные: `provides.scenes` и `entry.scene` не переименованы и не изменены, `properties`
сущности — только примитивы, `specVersion` остаётся `"1.0"`. Код не писался: ни валидатор, ни
резолвер, ни рантайм.

## Решения по формату: неясно / решил / откат

| Неясно | Решил | Откат |
|---|---|---|
| Как записать связь сцены с ресурсом: отдельный файл, словарь или поле манифеста | поле `provides.sceneEntries` — массив `{id, resource}`, аддитивно к `provides.scenes`; словарь отвергнут, потому что порядок объявлений и построчный дифф важнее O(1) доступа в контракте | убрать `sceneEntries` из схемы (поле необязательное); модули, которые его не пишут, ничего не заметят |
| Обязан ли `id` записи входить в `provides.scenes` | да, обязан: `scenes` — словарь сборки, `sceneEntries` — только его связь с файлами. Проверка семантическая (`scene.entry.unknown`), потому что JSON Schema не сравнивает два поля одного документа | снять правило и обновить строку кода в `errors.md`; форма записи не меняется |
| Грамматика `resource`: как запретить `..` и абсолютные пути одной строкой | `^res://(?!.*\.\.)[A-Za-z0-9_][A-Za-z0-9_./-]*\.tscn$`: префикс `res://` отсекает абсолютные пути, lookahead запрещает `..`, расширение фиксировано | ослабить шаблон до `^res://.*\.tscn$` и перенести запрет `..` в семантику валидатора |
| Где ловятся дубли сцен | дословно совпадающие записи — структурно (`uniqueItems`, код `field.unique`); дубль одного `id` с разными ресурсами и дубли между модулями — семантически (`scene.duplicate`, K-3) | оставить только структурную проверку; тогда разные ресурсы под одним ID пройдут молча — это ухудшение, не рекомендуется |
| Грамматика `entities[].id` | префикс `entity.`, как `scene.` у сцен: `^entity(\.[a-z][a-z0-9]*(-[a-z0-9]+)*)+$` | разрешить односегментные ID (`entity: "player"`), если авторам это окажется тесно |
| Что считать «только примитивами» в `properties` | `anyOf` из `string`/`number`/`boolean`/`null`; вложенный объект или массив — `field.type`. Объединение типов в `type` не используется: строгий Ajv такое запрещает | заменить `anyOf` на явный `$defs.primitive` со списком `type`, когда Ajv разрешит объединения |
| Нужны ли сущностям ключи локализации | в `properties` живут данные, а видимое имя — ключ каталога (`nameKey`); ключ описывает текст и не дублирует состояние экземпляра | если понадобится отдельное поле для ключа, добавить его аддитивно рядом с `properties` |
| Куда отнести коды `runtime.engine.missing` и `cli.dependency.node-missing`: это не форма документа и не граф модулей | в `semantic`/K-3: предусловие проверки, а не её результат. Реестр знает ровно три стадии, и связка «стадия → карточка» проверяется тестом, который в Scope этой карточки не входит | ввести четвёртую стадию `runtime` и поправить тест отдельной карточкой; меняется только поле `stage` (и вместе с ним `implementedIn`) |
| Имя кода `cli.dependency.node_missing`: карточка пишет его с подчёркиванием | `cli.dependency.node-missing`: шаблон кода в схеме реестра и в проверке разрешает только `[a-z0-9-]`, подчёркивание запрещено | расширить шаблон кода и проверку до `_` и переименовать обратно — одна строка в схеме реестра и в тесте |
| Строки текста для шести новых кодов | не добавлены: каталоги `locales/<locale>.json` ведёт карточка локализации, у контрактной карточки этой зоны нет. До появления строк диагностика рендерится `locale.key.missing`, код и `params` остаются верными | добавить 6 ключей в восемь каталогов и в базовый каталог валидатора одной карточкой локализации, ничего не меняя в контракте |
| Расхождение с кодом ядра: каким кодом сообщать, что `entry.scene` не разрешается в запускаемую сцену | по решению приёмки от 2026-11-07 (ADR по имени кода N-3, вариант B) единственное имя для этого случая — `ref.unresolved`: стадия `resolution`, карточка K-4, params `path`, `expected`, `actual`, extraParams `refKind = "scene"` и `providedBy`. `scene.entry.unknown` остаётся за правилом `provides.sceneEntries[].id` (стадия `semantic`, K-3) и второго смысла не получает; третьего имени для разрешения `entry.scene` нет. Выравнивание кода в `cli/` — карточка S-3R.2 | вернуть прежнюю формулировку (исходная редакция строки — коммит `ec8476f`) и оставить расхождение открытым; реестр и контракты при этом не меняются |
| Проверяются ли семантические фикстуры оракулом | нет: `check:contracts` исполняет только наборы `CASE_SETS` и стадии `schema`/`parse`, а тесты в Scope не входят. Фикстуры лежат в `schema/examples/scene-binding/` как эталон для валидатора K-3 и не выдаются за пройденную проверку | добавить набор `scene-binding` в `CASE_SETS` и реализовать семантические шаги в тестах отдельной карточкой |

### Уточнение по решению приёмки от 2026-11-07 (ADR по имени кода N-3, вариант B)

Это уточнение формулировки, а не новое решение: правила и откаты таблицы выше не меняются, статус
файла и дата принятия остаются прежними.

- Имя кода для случая «`entry.scene` не разрешается в запускаемую сцену» — `ref.unresolved`
  (стадия `resolution`, K-4): params `path`, `expected`, `actual`, extraParams `refKind = "scene"` и
  `providedBy`. Имя уже зафиксировано в [`schema/error-registry.json`](../../schema/error-registry.json)
  и в контрактах: [`module-manifest.md`](../contracts/module-manifest.md) прямо требует
  `extraParams.refKind = "scene"`, [`gamespec.md`](../contracts/gamespec.md) ссылается на тот же код
  для неразрешённой `entry.scene`. Нового имени не вводится.
- `scene.entry.unknown` остаётся за правилом N-4: `provides.sceneEntries[].id` обязан входить в
  `provides.scenes` (стадия `semantic`, K-3). Второго смысла у этого кода нет.
- Исходная формулировка строки «Расхождение с кодом ядра» — редакция файла до этого уточнения,
  коммит `ec8476f` (PR #24). Она сохранена в истории и приведена здесь ссылкой, а не пересказом.
- Выравнивание кода в `cli/` — зона владельца `cli/`, карточка S-3R.2; контрактные файлы и реестр
  этой карточкой не меняются.

## S-10 · Диагностика CLI: коды в реестре и правило `catalogKey`

Базовый срез — `main` на `f821d0e5`. Карточка меняет только контракт, реестр и тесты: реализация в
`game/**` остаётся за отдельной карточкой зоны `game/**`.

### Что решено и зачем

1. **Одна форма кода.** Реестр и §9 знают `cli.dependency.node-missing`. Подчёркиваний в кодах не бывает: остаётся форма
   `cli.dependency.node-missing`, и в реестре, и в контракте, и в реализации.
2. **`cli.run.render_failed` не заводится в реестре.** Этот код печатался при падении рендера и при
   выводе подменялся ключом `errors.runtime.engine.missing`. Вариант «зарегистрировать новый код и
   добавить восемь текстов» отклонён: у случая одна причина — движок не отрендерил кадры, а
   различающая машинная информация (`exit_code`, `frames`, `stderr`) уже приходит в `params.actual`.
   Выбран вариант «перенацелить код»: диагностика сообщает `runtime.engine.missing`, override не
   нужен, правило `catalogKey = "errors." + code` работает без исключений.
3. **`cli.usage` зарегистрирован.** Ключ `errors.cli.usage` уже был во всех восьми каталогах, но
   строки в реестре не было — реестр и каталоги расходились в обратную сторону. Код добавлен
   (стадия `semantic`, K-3, код возврата 2) с params `path`, `expected`, `actual` и extraParams
   `command`. Реестр и каталоги теперь совпадают в обе стороны, и это проверяет тест.
4. **Локаль вне набора — ошибка использования.** `--lang zh_CN` не должен превращаться ни в
   молчаливый английский, ни в «движок недоступен»: правило записано в
   [`localization.md`](../contracts/localization.md), раздел «Имя локали вне набора» — код
   `field.enum`, `params.expected` из восьми локалей, код возврата 2, проверка раньше проверок
   окружения.
5. **Расхождения под стражей.** `tests/contracts/cli-diagnostics.test.mjs` сверяет реестр с восемью
   каталогами в обе стороны, разбирает вызовы `_emit_catalog_error` в `game/cli/main.gd` и падает на
   любом коде мимо реестра и любом override, которых нет в списке.

### Неясно / решил / откат

| Неясно | Решил | Откат |
|---|---|---|
| Регистрировать `cli.usage` или убрать ключ из каталогов? | Зарегистрировать: ключ уже используется валидатором и резолвером, тексты есть во всех восьми каталогах | удалить строку `cli.usage` из реестра и абзац из `errors.md`; каталоги не трогаются |
| Что делать с локалью вне набора: silently `allow` или ошибка? | Ошибка `field.enum` (код возврата 2) с явным правилом в `localization.md`; `en`-нормализация остаётся только для значений GameSpec | убрать раздел «Имя локали вне набора» из `localization.md`; `field.enum` продолжает работать как общий код перечислений |

### Границы

Файлы реализации не менялись: `game/cli/main.gd`, `locales/*.json`, `tests/cli/**` остаются как на
`f821d0e5`. Схемы, `.github/workflows/**`, `tools/godot/**` и патчи не менялись (INV-2).

## S-14 · Отдельный код для нечитаемого файла действий `--input`

Базовый срез — `main` на `9de2da0706e42594e43ce6a6a6d006326313263b` (после S-13). В реестре 24 кода:
23 прежних не удалены и не переименованы, добавлен один.

| Что | Значение |
|---|---|
| Код | `actions.file.missing` |
| Область | документ прогона: файл действий, который `run --input` читает уже после GameSpec |
| Стадия | `semantic`: файл существует и читается — это смысл входных данных, а не форма документа |
| Владелец | K-3, карточка S-14; вызовы в `game/cli/main.gd` переключает S-15 |
| `params` | `path`, `expected`, `actual`; `extraParams` — `file` (путь к файлу действий) |
| `catalogKey` | `errors.actions.file.missing`; ключ есть во всех восьми каталогах |

**Почему не `spec.file.missing`.** `spec.file.missing` описывает документ GameSpec: у него `path` —
`/spec`, а текст говорит о файле спецификации. У `--input` другой документ (JSON-действия для
детерминированного прогона) и другой путь (`/--input`). Один код на два разных документа заставляет
человека читать текст про спецификацию там, где спецификация уже прочитана, и не даёт отличить промах в
пути к спеке от промаха в пути к действиям, не заглядывая в `params.path`. Поведение `spec.file.missing`,
`cli.dependency.node-missing` и `runtime.engine.missing` не меняется (N-8).

**Что меняет S-15.** Только вызовы: `_read_input_actions` в `game/cli/main.gd` (отсутствующий файл —
строка 263, нечитаемый — 267) начнёт сообщать `actions.file.missing` вместо `spec.file.missing`, с тем же
`path = /--input`, тем же кодом возврата 1 и теми же `params` (`expected`, `actual`, `file`). Эта карточка
поведение CLI не меняет: на срезе `9de2da0` прогон с отсутствующим `--input` по-прежнему даёт rc 1 и
`spec.file.missing`, тест «public run --input … localizes a missing input file» зелёный без правок.

**Сторож не снят.** Правила S-10 и запись S-12 в силе: `catalogKey = "errors." + code` без override,
код есть в реестре, ключ есть во всех восьми каталогах. Новый код проходит сторож
`tests/contracts/cli-diagnostics.test.mjs` (реестр ↔ каталоги в обе стороны, списки расхождений пусты).

**Границы.** За пределами перечисленных файлов изменена одна константа:
`tests/i18n/catalogs.test.mjs` (строки 20 и 28) — ожидаемое число базовых ключей 29 → 30. Тест сверяет
состав каталогов точным равенством, поэтому без этой правки он краснеет от самого факта нового ключа;
строгость не снижена (равенство осталось точным), и это единственная правка в `tests/**`.

**Откат.** Удалить строку реестра, строку таблицы в `errors.md`, ключ из восьми каталогов и этот раздел
одним коммитом; `spec.file.missing` продолжает работать как раньше, потому что вызовы ещё не
переключены — в этом и смысл разделения S-14 и S-15.
