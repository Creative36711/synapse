# SYN-2 · S-1 · Связь сцены с ресурсом и определения сущностей

- **Миссия:** SYN-2, карточка **S-1** «Контракт: `provides.sceneEntries` и `entities`»
- **Дата:** 2026-11-07
- **Автор:** Contract Architect
- **Область записи:** `schema/**`, `docs/contracts/**`, этот файл
- **Приёмка:** Warden (контракт), Spec Auditor (соответствие кода контракту)

Статус: accepted

## Что решено и зачем

Манифест получает законный способ связать смысловой ID сцены с ресурсом `.tscn`, а GameSpec —
способ описать сущность, не протаскивая в определение изменяемое состояние. До этой карточки связь
существовала только в коде ядра (таблица `game/runtime/scene_registry.gd`), то есть сцену нельзя было
добавить без правки ядра — это нарушало INV-11.

Изменения аддитивные: `provides.scenes` и `entry.scene` не переименованы и не изменены, `properties`
сущности — только примитивы, `specVersion` остаётся `"1.0"`. Код не писался: ни валидатор, ни
резолвер, ни рантайм.

## Решения по формату: неясно / решил / откат

| Неясно | Решил | Откат |
|---|---|---|
| Как записать связь сцены с ресурсом: отдельный файл, словарь или поле манифеста | поле `provides.sceneEntries` — массив `{id, resource}`, аддитивно к `provides.scenes`; словарь отвергнут, потому что порядок объявлений и построчный дифф важнее O(1) доступа в контракте | убрать `sceneEntries` из схемы (поле необязательное); модули, которые его не пишут, ничего не заметят |
| Обязан ли `id` записи входить в `provides.scenes` | да, обязан: `scenes` — словарь сборки, `sceneEntries` — только его связь с файлами. Проверка семантическая (`scene.entry.unknown`), потому что JSON Schema не сравнивает два поля одного документа | снять правило и обновить строку кода в `errors.md`; форма записи не меняется |
| Грамматика `resource`: как запретить `..` и абсолютные пути одной строкой | `^res://(?!.*\.\.)[A-Za-z0-9_][A-Za-z0-9_./-]*\.tscn$`: префикс `res://` отсекает абсолютные пути, lookahead запрещает `..`, расширение фиксировано | ослабить шаблон до `^res://.*\.tscn$` и перенести запрет `..` в семантику валидатора |
| Где ловятся дубли сцен | дословно совпадающие записи — структурно (`uniqueItems`, код `field.unique`); дубль одного `id` с разными ресурсами и дубли между модулями — семантически (`scene.duplicate`, K-3) | оставить только структурную проверку; тогда разные ресурсы под одним ID пройдут молча — это ухудшение, не рекомендуется |
| Грамматика `entities[].id` | префикс `entity.`, как `scene.` у сцен: `^entity(\.[a-z][a-z0-9]*(-[a-z0-9]+)*)+$` | разрешить односегментные ID (`entity: "player"`), если авторам это окажется тесно |
| Что считать «только примитивами» в `properties` | `anyOf` из `string`/`number`/`boolean`/`null`; вложенный объект или массив — `field.type`. Объединение типов в `type` не используется: строгий Ajv такое запрещает | заменить `anyOf` на явный `$defs.primitive` со списком `type`, когда Ajv разрешит объединения |
| Нужны ли сущностям ключи локализации | в `properties` живут данные, а видимое имя — ключ каталога (`nameKey`); ключ описывает текст и не дублирует состояние экземпляра | если понадобится отдельное поле для ключа, добавить его аддитивно рядом с `properties` |
| Куда отнести коды `runtime.engine.missing` и `cli.dependency.node-missing`: это не форма документа и не граф модулей | в `semantic`/K-3: предусловие проверки, а не её результат. Реестр знает ровно три стадии, и связка «стадия → карточка» проверяется тестом, который в Scope этой карточки не входит | ввести четвёртую стадию `runtime` и поправить тест отдельной карточкой; меняется только поле `stage` (и вместе с ним `implementedIn`) |
| Имя кода `cli.dependency.node_missing`: карточка пишет его с подчёркиванием | `cli.dependency.node-missing`: шаблон кода в схеме реестра и в проверке разрешает только `[a-z0-9-]`, подчёркивание запрещено | расширить шаблон кода и проверку до `_` и переименовать обратно — одна строка в схеме реестра и в тесте |
| Строки текста для шести новых кодов | не добавлены: каталоги `locales/<locale>.json` ведёт карточка локализации, у контрактной карточки этой зоны нет. До появления строк диагностика рендерится `locale.key.missing`, код и `params` остаются верными | добавить 6 ключей в восемь каталогов и в базовый каталог валидатора одной карточкой локализации, ничего не меняя в контракте |
| Расхождение с кодом ядра: CLI отдаёт `scene.id.unknown`, реестр знает `scene.entry.unknown` | реестр фиксирует имя по карточке; выравнивание кода — карточка владельца зоны `cli/` (INV-11: ядро не правится контрактной карточкой) | принять имя `scene.id.unknown` в реестре и убрать `scene.entry.unknown` — одна строка |
| Проверяются ли семантические фикстуры оракулом | нет: `check:contracts` исполняет только наборы `CASE_SETS` и стадии `schema`/`parse`, а тесты в Scope не входят. Фикстуры лежат в `schema/examples/scene-binding/` как эталон для валидатора K-3 и не выдаются за пройденную проверку | добавить набор `scene-binding` в `CASE_SETS` и реализовать семантические шаги в тестах отдельной карточкой |

## Инварианты

| Инвариант | Как выполнен |
|---|---|
| INV-1: локально, без сети, аккаунта и секретов | схемы без внешних `$ref`, `$id` в `.invalid`; существование ресурса — файловая проверка, без импорта движка и сети |
| INV-2: `tools/godot/**` и патчи не менялись | в диффе карточки нет ни одного файла `tools/godot/**` |
| INV-3: логика по смысловым ID, а не путям | путь к ресурсу существует ровно в одном месте — `provides.sceneEntries[].resource`; `entry.scene` и `provides.scenes` остаются ID |
| INV-4: определения без изменяемого состояния | `sceneEntry` и `entity` закрыты (`additionalProperties: false`), полей `state`/`save`/`runtime` нет, `properties` — только примитивы |
| INV-11: сцену можно добавить без правки ядра | модуль объявляет сцену в манифесте; связь ID↔ресурс больше не требует таблицы в `game/` |
| INV-13/INV-14: текст вне контракта, диагностика код+параметры | в контракте только `catalogKey`; у всех шести кодов базовые `params` и `additionalProperties`-безопасные добавки |

## Границы

Карточка не пишет реализацию: валидатор, резолвер сцен и рантайм — вне её. `provides.scenes` и
`entry.scene` не менялись. Строки текста в контракт не вводились. Реестр описывает коды, но не
проверяет их исполнением — это работа K-3 и последующих карточек.
