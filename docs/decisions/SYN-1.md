## Ратификация: решение Мастера от 2026-11-05

Открытый вопрос по формату закрыт фактическим ответом Мастера. Это ратификация уже реализованного
варианта, а не переопределение решений O-3…O-7 и не изменение формата или поведения ядра.

**Принят вариант A.** Описания — YAML 1.2 core schema; структурные схемы — JSON Schema 2020-12;
ошибка — `code` и `params(path, expected, actual)`, текст только из каталога перевода по
`catalogKey`; реестр ошибок — JSON.

**Варианты B и C отвергнуты:** B («только JSON») — нет комментариев и шумная пунктуация в
авторских файлах; C (собственный текстовый формат / TOML) — требует самописного парсера и
самописной схемы при нулевой экосистеме инструментов.

Источник решения — публично доступная страница обратной связи в Notion (ссылка выше); закрытый
процессный контур в обоснование не входит. Дата решения — 2026-11-05, до этой даты статус записи
был `proposed`, и вариант по умолчанию не считался принятием.

## Контекст

K-2 фиксирует контракты до реализации валидатора (K-3) и резолвера (K-4). Контракт читают:

- автор игры — глазами, в редакторе, без нашего кода;
- валидатор K-3 — машинно, по схеме;
- резолвер K-4 — машинно, по графу модулей;
- ревьюер и аудитор — в диффе PR.

Из этого следуют требования, которые и определили выбор:

1. Описание игры должно быть читаемым и комментируемым — это авторский артефакт, а не конфиг сервиса.
2. Структурная проверка должна быть стандартной и не требовать самописного парсера схем.
3. Диагностика должна быть машинной и переводимой: `code` + `params`, текст — из каталога (INV-6,
   INV-9).
4. Проверка обязана работать офлайн, без cortex, аккаунта и секретов (INV-1).
5. Логика адресуется смысловыми ID, а не путями ассетов (INV-3).

## Решение (принято 2026-11-05)

1. **Формат описаний — YAML 1.2 (core schema).** Комментарии, минимум пунктуации, построчный дифф,
   надмножество JSON.
2. **Правила чтения — часть контракта:** повтор ключа и merge-ключ `<<` запрещены, теги не
   исполняются, даты и `yes/no` не преобразуются неявно.
3. **Структурные схемы — JSON Schema 2020-12** с `additionalProperties: false` и локальными `$ref`
   в `$defs`. `$id` — в зоне `.invalid`, внешних ссылок нет: сеть не нужна.
4. **Ошибка — `code` + `params(path, expected, actual)`**; `catalogKey` строго `errors.<code>`.
   Текста ошибки в реестре нет.
5. **Реестр ошибок — JSON**, потому что это машинный артефакт с собственной схемой, а не авторский
   текст.
6. **Каждый контракт имеет пример «валидно» и «невалидно»**, привязанный к коду и пути в
   `cases.json`; проверка сверяет их и падает при расхождении.

## Варианты

| Вариант | Плюсы | Минусы | Итог |
|---|---|---|---|
| **A. YAML + JSON Schema 2020-12 + `code`/`params`** | читаемо автором, схемы стандартные, дифф чистый, JSON-проекция бесплатна | нужны строгие правила чтения YAML (повторы, теги) | **принят 2026-11-05 (K-22)** |
| B. Только JSON | один формат для людей и машин, нет вопросов к YAML | нет комментариев, шумная пунктуация, авторские правки тяжело ревьюить | отвергнут 2026-11-05 |
| C. Свой текстовый формат / TOML | полный контроль | самописный парсер и самописная схема, экосистема инструментов нулевая | отвергнут 2026-11-05 |

Смена варианта не меняла бы грамматику полей, коды ошибок и `params`: переписывается сериализация и
примеры, а смысл контракта остаётся. Принятый вариант A это и зафиксировал.

## Последствия

- Появляется одна команда проверки — `npm run check:contracts`, офлайн, без сервисов.
- Контракт нельзя «расширить на месте»: лишнее поле — ошибка, а не молчание.
- Автор обязан писать ключи каталога вместо текста; это дороже на старте и дешевле при восьми локалях.
- Появляются devDependencies (`ajv`, `yaml`) — только для проверки, не для рантайма.
- Ошибки становятся машинными: UI собирает фразу из каталога, а не печатает строку из кода.

## Обратимое решение: CJK fonts for O-13 (K-29, D-016 variant C)
- **Неясно:** как закрепить проверяемую офлайн-доставку семейств Noto Sans JP/KR/SC без новых runtime-зависимостей и без подмены исходных файлов шрифтов.
- **Решил:** добавить неизменённые `@expo-google-fonts/noto-sans-jp`, `noto-sans-kr`, `noto-sans-sc` версии `0.4.4` (SIL OFL 1.1) в `game/theme/fonts/`, с `fonts.manifest.json`, полным `LICENSE_FONT` и append-only NOTICE; точные размеры, cmap glyph counts и SHA-256 зафиксированы в манифесте.
- **Откат:** удалить только три перечисленных TTF, `LICENSE_FONT`, `fonts.manifest.json`, эту запись и добавленный в конец NOTICE раздел о CJK; остальные строки NOTICE и существующие манифесты/хэши оставить без изменений.

## Обратимое решение: базовый Noto Sans для латиницы и кириллицы (K-31)
- **Неясно:** как доставить базовый Noto Sans в репозитории без runtime-зависимостей и без изменения CJK-файлов K-29.
- **Решил:** добавить исходный `NotoSans_400Regular.ttf` из `@expo-google-fonts/noto-sans@0.4.2` (SIL OFL 1.1), его отдельную лицензию и запись с SHA-256/размером в манифест; тему не настраивать в K-31.
- **Откат:** удалить только базовый TTF, `LICENSE_FONT_NOTO_SANS`, запись и сумму из манифеста, добавленный в конец NOTICE раздел и эту запись; CJK-файлы, их лицензию и прежние NOTICE строки оставить.

## Обратимое решение: локализованный fallback-стек для K-30
- **Неясно:** контрольная строка `こんにちは世界ゲーム안녕` не покрывается каждым TTF по отдельности: базовый Noto Sans не содержит CJK, а JP/SC не содержат Hangul.
- **Решил:** проверять контрольную строку по эффективной цепочке fallback каждого locale-стека, одновременно требуя наличие всех четырёх шрифтов и первым CJK-семейством ставить JP для ja, KR для ko, SC для zh-Hans; визуальный O-13 остаётся обязательным и неизменным.
- **Откат:** изменить только verifier и эту запись после уточнения смысла cmap-проверки; не менять шрифтовые файлы и не ослаблять требование об отсутствии tofu.

## Обратимое решение: каталог GameSpec-fixture для K-32
- **Неясно:** O-12 требует валидировать исходный graph fixture напрямую, но у него отсутствует игровой каталог заголовочного ключа.
- **Решил:** аддитивно добавить `tests/modules/fixtures/locales/en.json` для `game.synapse_test_graph.title`; GameSpec по умолчанию поддерживает только `en`, а `--locale de` локализует диагностику, не изменяя поддерживаемые игрой локали.

## Обратимое решение: `oracle_cli_path` — фактическая точка входа CLI (K-37)

- **Контекст:** в §5 SYN-1 названа команда с `res://cli/synapse.gd`, но такого файла в репозитории нет. Реальная публичная точка входа — `game/cli/main.gd`, путь Godot — `res://cli/main.gd`.
- **Решение Coordinator по делегированию Мастера (2026-11-06, статус: accepted):** проверять CLI через фактическую публичную точку входа `res://cli/main.gd`. Сохранить без ослабления требования §5 к argv, диагностике, кодам возврата и буквальным ограничениям: без сети, cortex, аккаунта и секретов. Решение согласует документацию с существующей реализацией и не меняет oracle.
- **Последствия:** K-36 остаётся принятой (`Accepted`, `Check=pass`). Буквальная команда §5 с `res://cli/synapse.gd` завершается сообщением `File not found`, RC=1; это зафиксированное расхождение пути, а не повод менять CLI, критерии или диагностику. Команды документации и регрессионные проверки используют `res://cli/main.gd`.
- **Откат:** пересмотреть только эту запись и ссылку на CLI в документации при явном повторном решении о пути; не удалять и не менять критерии §5, CLI или тесты в рамках такого отката.

## Обратимое решение: `oracle_render_entry` — фактическая точка входа рендера образца шрифта (K-40)

- **Контекст:** O-13 в §5 SYN-1 можно прочитать как запуск примера игры, однако фактический визуальный тест шрифтов — отдельная сцена `res://theme/render_locale.tscn`, запускаемая npm-скриптом `render:font-sample`. Без документированной команды проверка невоспроизводима. Рантайм и шрифты менять не требуется.
- **Решение Coordinator по делегированию Мастера (2026-11-06, статус: accepted):** документировать фактический путь запуска в отдельном разделе `AGENTS.md`: `SYNAPSE_GODOT_MODE=offscreen K30_LOCALE=<locale> K30_OUTPUT=<absolute-png-path> npm run render:font-sample`, где npm-скрипт выполняет `godot --path game res://theme/render_locale.tscn`. Использовать только контрактные локали `ja`, `ko`, `zh-Hans`, `en`; `zh_CN` из формулировки ТЗ сопоставляется с `zh-Hans`, файл `zh_CN.json` не добавлять.
- **Последствия:** O-13 **не ослабляется**: для `ja`, `ko`, `zh-Hans` создаются свежие PNG на актуальном `main`, `en` служит контрольным рендером; исполнитель открывает и визуально проверяет каждый PNG на tofu-глифы. Машинные проверки cmap/стека могут только дополнять визуальную проверку и не заменяют её. Имена локалей и файлов шрифтов, `fonts.manifest.json`, `LICENSE_FONT` и рантайм остаются неизменными.
- **Откат:** удалить только этот раздел и добавленный раздел рендера O-13 в `AGENTS.md`, если будет принято новое явное решение о фактическом entry point. Не удалять и не менять критерии O-13, шрифты, манифест или runtime в рамках отката.
