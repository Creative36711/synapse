## Ратификация: решение Мастера от 2026-11-05

Открытый вопрос по формату закрыт фактическим ответом Мастера. Это ратификация уже реализованного
варианта, а не переопределение решений O-3…O-7 и не изменение формата или поведения ядра.

**Принят вариант A.** Описания — YAML 1.2 core schema; структурные схемы — JSON Schema 2020-12;
ошибка — `code` и `params(path, expected, actual)`, текст только из каталога перевода по
`catalogKey`; реестр ошибок — JSON.

**Варианты B и C отвергнуты:** B («только JSON») — нет комментариев и шумная пунктуация в
авторских файлах; C (собственный текстовый формат / TOML) — требует самописного парсера и
самописной схемы при нулевой экосистеме инструментов.

Источник решения — публично доступная страница обратной связи в Notion (ссылка выше); закрытый
процессный контур в обоснование не входит. Дата решения — 2026-11-05, до этой даты статус записи
был `proposed`, и вариант по умолчанию не считался принятием.

## Контекст

K-2 фиксирует контракты до реализации валидатора (K-3) и резолвера (K-4). Контракт читают:

- автор игры — глазами, в редакторе, без нашего кода;
- валидатор K-3 — машинно, по схеме;
- резолвер K-4 — машинно, по графу модулей;
- ревьюер и аудитор — в диффе PR.

Из этого следуют требования, которые и определили выбор:

1. Описание игры должно быть читаемым и комментируемым — это авторский артефакт, а не конфиг сервиса.
2. Структурная проверка должна быть стандартной и не требовать самописного парсера схем.
3. Диагностика должна быть машинной и переводимой: `code` + `params`, текст — из каталога (INV-6,
   INV-9).
4. Проверка обязана работать офлайн, без cortex, аккаунта и секретов (INV-1).
5. Логика адресуется смысловыми ID, а не путями ассетов (INV-3).

## Решение (принято 2026-11-05)

1. **Формат описаний — YAML 1.2 (core schema).** Комментарии, минимум пунктуации, построчный дифф,
   надмножество JSON.
2. **Правила чтения — часть контракта:** повтор ключа и merge-ключ `<<` запрещены, теги не
   исполняются, даты и `yes/no` не преобразуются неявно.
3. **Структурные схемы — JSON Schema 2020-12** с `additionalProperties: false` и локальными `$ref`
   в `$defs`. `$id` — в зоне `.invalid`, внешних ссылок нет: сеть не нужна.
4. **Ошибка — `code` + `params(path, expected, actual)`**; `catalogKey` строго `errors.<code>`.
   Текста ошибки в реестре нет.
5. **Реестр ошибок — JSON**, потому что это машинный артефакт с собственной схемой, а не авторский
   текст.
6. **Каждый контракт имеет пример «валидно» и «невалидно»**, привязанный к коду и пути в
   `cases.json`; проверка сверяет их и падает при расхождении.

## Варианты

| Вариант | Плюсы | Минусы | Итог |
|---|---|---|---|
| **A. YAML + JSON Schema 2020-12 + `code`/`params`** | читаемо автором, схемы стандартные, дифф чистый, JSON-проекция бесплатна | нужны строгие правила чтения YAML (повторы, теги) | **принят 2026-11-05 (K-22)** |
| B. Только JSON | один формат для людей и машин, нет вопросов к YAML | нет комментариев, шумная пунктуация, авторские правки тяжело ревьюить | отвергнут 2026-11-05 |
| C. Свой текстовый формат / TOML | полный контроль | самописный парсер и самописная схема, экосистема инструментов нулевая | отвергнут 2026-11-05 |

Смена варианта не меняла бы грамматику полей, коды ошибок и `params`: переписывается сериализация и
примеры, а смысл контракта остаётся. Принятый вариант A это и зафиксировал.

## Последствия

- Появляется одна команда проверки — `npm run check:contracts`, офлайн, без сервисов.
- Контракт нельзя «расширить на месте»: лишнее поле — ошибка, а не молчание.
- Автор обязан писать ключи каталога вместо текста; это дороже на старте и дешевле при восьми локалях.
- Появляются devDependencies (`ajv`, `yaml`) — только для проверки, не для рантайма.
- Ошибки становятся машинными: UI собирает фразу из каталога, а не печатает строку из кода.

## Обратимые решения (неясно / решил / откат)

| Неясно | Решил | Откат |
|---|---|---|
| Где держать контрактные примеры: `docs/contracts/examples/**` или `schema/examples/**` | `schema/examples/**` — примеры рядом со схемами, которую они проверяют | перенести каталог и поправить `cases.json` (пути в них относительные) |
| Где держать скрипт проверки: `scripts/` или `tests/contracts/` | `tests/contracts/check-contracts.mjs` — Scope карточки разрешает `tests/contracts/**` и не разрешает `scripts/**` | перенести файл и строку `scripts.check:contracts` в `package.json` |
| Имя файла записи решения | `docs/decisions/SYN-1.md` — так назван путь в Scope карточки | переименовать файл; тест ищет статус в этом пути |
| Нужна ли строка `node_modules/` в `.gitignore` | добавил: без неё `git add -A` затянет зависимости в коммит | удалить строку, если ревью сочтёт её выходом за Scope |
| Формат реестра ошибок: YAML или JSON | JSON — машинный артефакт, проверяется своей схемой, автор его не редактирует | перевести в YAML и читать тем же строгим загрузчиком |
| Минимальная версия Node | `>=20.19.0` (в песочнице 22.22.3, `node --test` и ESM без флагов) | поднять порог в `engines`, ничего больше не меняя |
| Где CLI ищет игровые каталоги переводов в K-3 | `locales/<locale>.json` рядом с переданным GameSpec; так путь однозначен для нескольких игр и тестовых fixtures | изменить resolver и переместить `examples/**/locales` вместе; контракт полей не меняется |
| Где CLI ищет манифесты модулей в K-4 | сначала `<GameSpec stem>/modules`, затем `modules/` рядом с GameSpec, затем `game/modules/`; существующая структура `examples/cycle.game.yaml` сохраняется, поиск детерминирован и локален | изменить только приоритет каталогов и переместить тестовые манифесты, не меняя GameSpec/schema |
| Проверять ли `entry.scene`, когда в графе нет модулей | пустой граф — успешная no-op резолюция с `order: []`; сцену проверять только для непустой сборки, как требует O-6 для минимального примера | убрать условие пустого графа и обновить acceptance fixture после отдельного решения о предоставлении встроенной сцены |
| Значения локалей при отсутствии `locales` | нормализовать в `default: en`, `supported: [en]`; не объявлять неподтверждённые переводы | поменять только нормализацию и покрывающий тест, если Coordinator уточнит политику |
| Лицензионный файл в корне репозитория | `LICENSE` уже существует: MIT, `Copyright (c) 2026 Creative36711` (PR #7, коммит `0b680a3`); поле `license` в `package.json` — `MIT`, тексты согласованы (INV-8) | файл не удалять и не перелицензировать без решения Мастера; правка текста лицензии — отдельной карточкой |
| Где хранить core-каталоги K-6, не смешивая их с игровыми каталогами | `locales/<locale>.json` в корне — системные диагностические тексты; каталоги игры остаются рядом с GameSpec | перенести файлы и обновить загрузчик/проверку; формат GameSpec не меняется |
| Что именно означает fallback локализации | неподдерживаемый выбор локали нормализуется в `en`; отсутствующий ключ поддерживаемой локали не подменяется английским и возвращается как отсутствующий, сохраняя правило против тихой смеси языков из `docs/contracts/localization.md` | изменить поведение только после отдельного решения о fallback для пропуска ключа и согласовать его с контрактом локализации |
| Граница статического поиска UI-литералов K-6 | искать непустые прямые строковые присваивания display-полям в `.gd` и `.tscn` (`text`, `tooltip_text`, `placeholder_text`, `window_title`, `title`) | расширить анализатор и его fixtures при появлении иных соглашений UI; не исключать найденные литералы без каталога |
