# Контракты ядра · K-2

Проверяемые контракты описания игры и модуля: **GameSpec**, **манифест модуля**, **реестр кодов
ошибок**. Здесь только сами контракты и их проверка — валидатора, резолвера и рантайма в K-2 нет.

**Статус: формат принят** (2026-11-05, [`../decisions/SYN-1.md`](../decisions/SYN-1.md)):
описания — YAML 1.2 core schema, структурные схемы — JSON Schema 2020-12, ошибка — `code` +
`params(path, expected, actual)` с текстом из каталога. «Черновик формата» больше не действует:
схемы ниже — действующий контракт, а не предложение.

## Почему YAML

Контракт читает человек — автор игры, гейм-дизайнер, ревьюер без доступа к нашему коду. YAML
выбран по практическим причинам, а не по вкусу:

- **Комментарии и многострочный текст.** В JSON рядом с полем нельзя оставить объяснение, а в
  спецификации игры объяснения нужны чаще, чем в конфиге сервиса.
- **Меньше шума.** Нет кавычек у ключей, нет запятых в концах строк, нет экранирования путей — файл
  диффится построчно и читается в PR без парсера.
- **Один язык для людей и машин.** YAML 1.2 core schema — надмножество JSON: любой JSON-документ
  остаётся валидным YAML, поэтому машинная проекция бесплатна, а схемы не нужно переписывать.
- **Никакой семантики исполнения.** Это данные, а не код: нет вычислений, тегов, импортов.

Ограничения YAML компенсируются правилами чтения, а не доверием к парсеру:

1. **YAML 1.2, core schema.** Не поддерживаем YAML 1.1: `yes`/`no`/`on`/`off` остаются строками,
   даты без кавычек — строками, а не `Date`.
2. **Повтор ключа — ошибка** (`yaml.duplicate-key`). Молчаливое «последний выиграл» запрещено:
   иначе ошибка автора превращается в тихую потерю данных.
3. **Merge-ключ `<<` не поддерживается**: наследование YAML 1.1 не входит в core schema и в
   контракте выглядит как лишнее поле.
4. **Только безопасные теги.** `customTags` пуст, якоря ограничены `maxAliasCount`, файл не может
   вызвать исполнение кода или «billion laughs».
5. **Никаких сетевых резолвов.** `$id` схем — в зоне `.invalid` (RFC 2606), внешних `$ref` нет,
   проверка не делает ни одного HTTP-запроса (INV-1).

Структурные схемы — **JSON Schema 2020-12**: зрелый диалект с `$defs`, `additionalProperties`,
`uniqueItems` и точной семантикой `required`; один и тот же файл проверяет и YAML, и JSON-проекцию.

## Что именно проверяет K-2

Структурная проверка по схеме и правилам чтения:

- обязательные поля, типы, закрытые наборы значений, грамматики ID/версий/ключей, уникальность
  элементов (коды `field.*`);
- запрет лишних полей — контракт не расширяется «на месте» (`field.unknown`);
- безопасное чтение YAML: повтор ключа, синтаксис (`yaml.*`);
- реестр ошибок: у каждого кода есть `code`, `params(path, expected, actual)` и ключ каталога;
- сверка «реестр ↔ документация»: код без строки в `errors.md` и строка без кода — провал проверки.

## Границы: K-2, K-3, K-4

| Что | K-2 (эта карточка) | K-3 (валидатор) | K-4 (резолвер) |
|---|---|---|---|
| Схема, грамматики, реестр кодов, примеры | **да** | использует | использует |
| Отсутствие/тип/лишнее поле/шаблон | **да, статически по примерам** | да, на живом файле | — |
| Чтение YAML с запретом повторов ключей | **эталон в `tests/contracts/lib`** | переносит в CLI | использует |
| Ключи каталога существуют для локали | нет | **да** (`locale.key.missing`) | — |
| `default` входит в `supported`, смысловые ID сцен существуют | нет | **да** | — |
| Ресурс сцены существует, ID сцены не дублируется, файл спецификации читается | нет | **да** (`scene.*`, `spec.file.missing`) | — |
| Связь `sceneEntries` с `provides.scenes` | форма записи | **да** (`scene.entry.unknown`) | использует |
| Граф зависимостей, версии, конфликты, цикл | нет | нет | **да** |
| Рантайм, загрузка сцен | нет | нет | — (K-5) |

Семантические проверки (K-3) и разрешение графа модулей (K-4) здесь описаны как требования, но не
выполняются: их реализация — отдельные карточки. K-2 **не реализует** валидатор, резолвер, CLI и
рантайм и не закрывает долг O-2 из K-1. Примеры
ошибок в `schema/examples/**` — статические: они доказывают, что схема отсекает описанный ввод, и
не выдаются за работу резолвера. Цикл модулей K-2 не ищет: он фиксирует код диагностики и форму
графа, а обнаружение — K-4.

## Контракт ошибки

Ошибка — это машинный объект, а не строка:

```json
{
  "code": "field.unknown",
  "params": { "path": "/game/genre", "expected": "поле из контракта GameSpec 1.0", "actual": "genre" },
  "catalogKey": "errors.field.unknown"
}
```

- `code` и `params` — стабильны, не зависят от локали (INV-6, INV-10);
- `path` — JSON Pointer к значению (для отсутствующего/лишнего поля — к имени ключа);
- пользовательский текст берётся из каталога перевода по `catalogKey`, в коде и реестре его нет
  (INV-9).

Подробности и полный реестр — [`errors.md`](errors.md).

## Новые коды и что именно проверено

Связь сцены с ресурсом и определения сущностей добавлены контрактом (карточка S-1,
[`../decisions/SYN-2.md`](../decisions/SYN-2.md)). Честно про охват проверки:

- **Структурная часть** (`provides.sceneEntries`, `entities`) проверяется исполняемым оракулом:
  `schema/examples/**/cases.json` дают валидные и невалидные примеры, `check:contracts` сверяет код и
  путь ошибки.
- **Семантические коды** (`scene.entry.unknown`, `scene.duplicate`, `scene.resource.missing`,
  `spec.file.missing`, `runtime.engine.missing`, `cli.dependency.node-missing`) схема проверить не
  может: нужны файловая система, сборка модулей и окружение. Их эталонные фикстуры лежат в
  `schema/examples/scene-binding/`, но оракул `check:contracts` исполняет только наборы `CASE_SETS`
  и стадии `schema`/`parse`, поэтому эти фикстуры **не** выдаются за пройденную проверку: их
  исполняет валидатор K-3.
- **Тексты новых кодов** пока не добавлены в `locales/<locale>.json`: восемь каталогов ведёт карточка
  локализации. До появления строк диагностика рендерится штатным `locale.key.missing`; код и `params`
  от этого не меняются (INV-9, INV-14).

## Как проверить

```bash
npm ci                          # зависимости строго из package-lock.json, без сети после установки
npm run check:contracts         # оракул карточки
```

Успешный прогон печатает:

```
contract-check: files=6 tests=N pass=N fail=0
contract-check: ok
```

`check:contracts` запускает `node --test tests/contracts/*.test.mjs`, разбирает TAP-итог и падает,
если тестов ноль, есть `fail`, `cancelled` или `skipped`: «нечего проверять» не равно «всё хорошо».
Сама проверка офлайн: только `node_modules` из lockfile и файлы репозитория.

Отдельно, без npm:

```bash
node --test tests/contracts/*.test.mjs
```

## Инварианты

| Инвариант | Где виден в K-2 |
|---|---|
| INV-1: проверка локальна, без сети, закрытых контуров и секретов | схемы без внешних `$ref`, `$id` в `.invalid`, только devDependencies из lockfile |
| INV-2: контракт — единственный источник имён полей | схемы и таблицы полей в `gamespec.md` / `module-manifest.md` |
| INV-3: логика по смысловым ID, не по путям ассетов | `gameId`, `moduleId`, `entityId`, `sceneId`, `entry.scene`, `provides.scenes`; путь к ресурсу живёт только в `provides.sceneEntries[].resource` |
| INV-4: определения без изменяемого состояния | `additionalProperties: false` во всех объектах, запрет `state`/`runtime`/`save` |
| INV-5: цикл зависимостей — ошибка | код `module.dependency.cycle`, `extraParams.cycle`, реализация K-4 |
| INV-6: ошибка называет path/expected/actual | базовые `params` у каждого кода, проверяется тестом |
| INV-7: нет ветвлений по жанру | в контракте нет поля `genre`, пример `invalid/unknown-field.yaml` |
| INV-8: MIT-согласованность | `license: MIT` в `package.json`, проверяется тестом |
| INV-9: текст только из каталога | `catalogKey` вместо сообщений, схема реестра запрещает `message`/`text` |
| INV-10: локаль не меняет смысл проверки | локаль — только enum из §9; проверки от неё не зависят |

## Версионирование

- Поле `specVersion` (сейчас `"1.0"`) привязывает документ к версии контракта; несовпадение —
  `field.enum`, а не «попробуем прочитать».
- `$id` схем и `registryVersion` реестра меняются вместе с несовместимым изменением контракта.
- Совместимое добавление поля — новая версия схемы и запись в `docs/decisions/`.
