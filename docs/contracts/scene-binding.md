# Связывание сцены и сущности: что делает автор

Эта страница — для автора игры и модуля. Она отвечает на три вопроса: как объявить сцену,
что увидит `run`, и что означает каждая ошибка. Машинные контракты — в
[`module-manifest.md`](module-manifest.md) и [`gamespec.md`](gamespec.md); коды и `params` —
в [`errors.md`](errors.md).

## Как объявить сцену

Смысловой ID сцены объявляет модуль, а не файл игры. Игра адресует сцену ID (INV-3), модуль
сопоставляет ID ресурсу:

```yaml
provides:
  scenes: ["scene.main-menu", "scene.state-motion"]
  sceneEntries:
    - id: "scene.main-menu"
      resource: "res://runtime/scenes/main_menu.tscn"
    - id: "scene.state-motion"
      resource: "res://runtime/scenes/state_motion.tscn"
```

Три правила, которые проверяются:

1. `id` записи обязан входить в `provides.scenes` того же манифеста. Список `scenes` — словарь
   сборки, `sceneEntries` — его связь с файлами; запись «в обход» словаря не работает.
2. Один `id` — одна запись на всю сборку. Два модуля не могут сопоставить `scene.main-menu` разным
   файлам: это не «позднее объявление выиграло», а ошибка.
3. `resource` — путь движка: `res://`, расширение `.tscn`, без `..` и без абсолютных путей. Файл
   должен существовать в сборке.

В игре сцена выбирается смысловым ID, а не путём:

```yaml
entry:
  scene: "scene.main-menu"
```

## Как объявить сущность

```yaml
entities:
  - id: "entity.player"
    properties:
      max_health: 100
      walk_speed: 3.5
      can_dash: false
      nameKey: "game.example_minimal.entity_player.name"
```

- `id` — смысловой ID с префиксом `entity.`;
- `properties` — только примитивы (строка, число, булево, `null`);
- изменяемого состояния здесь нет: `state`, `save`, `runtime` — не поля контракта (INV-4);
- видимое игроку имя — ключ каталога (`nameKey`), а не строка текста (INV-9).

## Что увидит `run`

1. Валидация GameSpec и манифестов подключённых модулей. Ошибка — диагностика с кодом и `params`,
   код возврата 1, рендер не начинается.
2. Выбор сцены по `entry.scene`: ID ищется среди предоставленных `provides.scenes` и связывается с
   ресурсом через `sceneEntries`.
3. Проверка, что ресурс существует. Проверка файловая: сеть, импорт ассетов и запуск движка для неё
   не нужны.
4. Рендер сцены и, если запрошено, снимок состояния мира. Ошибки этого шага — свои коды
   (`runtime.engine.missing`, `cli.run.*`).

Чего `run` не делает: не угадывает путь по имени ID, не ищет файл «рядом», не подменяет
отсутствующий ресурс заглушкой и не считает пропуск проверки успехом.

## Что означает каждая ошибка

| Код | Когда | Что поправить |
|---|---|---|
| `scene.entry.unknown` | `sceneEntries[].id` не входит в `provides.scenes` | добавить ID в `scenes` или удалить запись |
| `scene.duplicate` | один ID сцены сопоставлен ресурсу дважды — в манифесте или между модулями | оставить одну запись, второй модуль убрать из сборки |
| `scene.resource.missing` | файла `res://…tscn` из записи нет в сборке | положить файл по указанному пути или исправить `resource` |
| `ref.unresolved` | смысловой ID ничем не предоставлен: `entry.scene` игры не входит в `provides.scenes` подключённых модулей (или не разрешается другой `refKind`), `providedBy` перечисляет, кто искал | подключить модуль, который объявляет ID в `provides.scenes`, или исправить ссылку на существующий ID; путь по имени ID не угадывается, заглушка не подставляется |
| `spec.file.missing` | CLI не может прочитать переданный файл спецификации | проверить путь, права и что это файл, а не каталог |
| `actions.file.missing` | файл, переданный в `run --input`, не читается: путь есть, а открыть не удалось (это не GameSpec — спецификация к этому моменту прочитана, у неё свой код `spec.file.missing`) | проверить аргумент `--input`: путь, права и что это файл, а не каталог; опечатку в имени исправить, заглушку не подставлять |
| `runtime.engine.missing` | движок, которым выполняется `run`, недоступен | установить движок и повторить `run` |
| `cli.dependency.node-missing` | для валидатора и резолвера нет Node.js нужной версии | установить Node.js и повторить проверку |
| `field.pattern` | `resource` не `res://…tscn`, содержит `..` или абсолютный путь | записать путь как `res://<каталог>/<файл>.tscn` |
| `field.unique` | одна и та же запись о сцене повторена дословно | оставить одну запись |

Каждая ошибка — это `code` + `params` (`path`, `expected`, `actual` и добавки вроде `sceneId`,
`resource`); текст для человека подставляется из каталога по `catalogKey` и на смысл проверки не
влияет (INV-10). Готовой фразы в контракте нет намеренно: строку в код не вписывают (INV-9).

## Где границы

- **K-2 (формат принят):** грамматика `sceneEntries` и `entities` в схемах, структурные коды
  `field.*`.
- **K-3 (валидатор):** существование ресурса, совпадение с `provides.scenes`, дубли между модулями,
  читаемость файла спецификации, доступность Node.js.
- **Рантайм:** запуск движка, рендер, снимок состояния. Появление самого резолвера сцен в коде — не
  эта карточка.

## Как проверить

```bash
npm run check:contracts     # схемы, примеры, реестр кодов, документация
node --test tests/contracts/*.test.mjs
```

валидный ввод и структурно валидный ввод, который обязан ловить валидатор своим кодом.
